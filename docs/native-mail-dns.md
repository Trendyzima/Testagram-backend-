# Testagram native mail DNS

The native mail transport is designed to send directly from a dedicated,
always-on SMTP host. It uses
`mail.testagram.site` as its SMTP EHLO hostname, signs messages with DKIM
(`d=testagram.site`, selector `tg2026`), and uses per-message VERP return
addresses at `bounces.testagram.site`.


## Hosting compatibility — production blocker

**The current InstaBox machine is not a suitable direct-MX mail host.** Its
public-port gateway publishes web URLs and raw TCP ports only in the range
1024–65535; it does not publish inbound TCP/25 or give this machine a dedicated
public SMTP IPv4 address. An outbound HTTP-observed address must not be treated
as an inbound mail-server address: it may be shared NAT egress. InstaBox machines
can also auto-pause, which is unsuitable for an always-on MX/feedback listener.

Keep the Testagram application on InstaBox if desired, but run the native SMTP
transport and feedback listener on a separate dedicated VPS with all of the
following confirmed by its provider:

- A stable, globally routable public IPv4 assigned to that VPS
- Inbound TCP/25 and outbound TCP/25 permitted
- PTR/rDNS control for that IPv4, set to `mail.testagram.site`
- A persistent, always-on service (no automatic idle suspension)
- Ability to install and renew a public TLS certificate for `mail.testagram.site`

Until that host exists, **do not publish mail DNS, claim direct-MX delivery, or
treat the InstaBox-local TCP/25 check as external reachability**. The current
InstaBox deployment deliberately skips native-mail DNS publication and does
not forward the Cloudflare DNS token into that machine. The DKIM key currently
generated by the InstaBox deployment is not yet a production mail-host key;
generate and persist the production key on the dedicated SMTP host before
publishing its DKIM record.

Do not publish placeholder IP addresses or placeholder DKIM keys. The deployment
script creates the private key on InstaBox and prints the matching public key. It also generates a separate
`TESTAGRAM_MAIL_VERP_KEY` on the VPS; this is distinct from the encrypted-outbox
key and is never supplied by an external mail provider. Keep the VERP key stable
while any return-path tokens remain valid (45-day token lifetime plus the
retention window); rotating it early invalidates pending bounce correlations. Inbound
SMTP advertises STARTTLS when a valid certificate and key are installed at
`/data/home/testagram/mail-tls/fullchain.pem` and
`/data/home/testagram/mail-tls/privkey.pem`.
Publish the records only after confirming the dedicated SMTP VPS public IPv4 address and that
all outbound mail for the bounce subdomain comes from this VPS.

## Automated Cloudflare DNS reconciliation

The standalone reconciler can manage the four dedicated mail DNS names
through the Cloudflare API, but it must be run only from the dedicated SMTP
host after that host is operational. Configure a narrowly scoped
`CLOUDFLARE_DNS_API_TOKEN` with access only to the `testagram.site` zone:
**Zone / Zone / Read** and **Zone / DNS / Edit**. Do not forward this token to
the InstaBox application deployment.

The reconciler requires an explicit `TESTAGRAM_NATIVE_MAIL_PUBLIC_IPV4` value; it never discovers an address through an outbound HTTP service. It discovers the zone, reads existing records, and only touches
`mail.testagram.site`, `bounces.testagram.site`,
`tg2026._domainkey.testagram.site`, and `_dmarc.testagram.site`. It fails
closed on ambiguous zone/record duplicates, leaves root MX records alone,
forces the SMTP A record to DNS-only, uses an initial SPF soft-fail policy, and
preserves any existing DMARC policy. It does not configure provider PTR/rDNS,
issue TLS certificates, or verify Gmail/Outlook delivery. It cannot make an InstaBox
machine receive SMTP on TCP/25.

## Required records

| Type | Name | Value |
|---|---|---|
| A | `mail.testagram.site` | The dedicated SMTP VPS public IPv4 address |
| MX | `bounces.testagram.site` | Priority 10, target `mail.testagram.site.` |
| TXT | `bounces.testagram.site` | `v=spf1 ip4:<DEDICATED_SMTP_VPS_PUBLIC_IPV4> ~all` during initial rollout; tighten to `-all` only after confirming no other senders use the bounce subdomain. |
| TXT | `tg2026._domainkey.testagram.site` | `v=DKIM1; k=rsa; p=<PUBLIC_KEY_FROM_DEPLOY_LOG>` |
| TXT | `_dmarc.testagram.site` | `v=DMARC1; p=none; adkim=r; aspf=r; rua=mailto:<MONITORED_REPORT_MAILBOX>` |

The SPF record belongs on **bounces.testagram.site**, because the SMTP MAIL FROM
address uses that subdomain. Publish exactly one SPF record at that name. The
`-all` policy is appropriate only after confirming there are no other legitimate
senders using `bounces.testagram.site`.

The DMARC report mailbox must exist and be monitored before it is placed in the
`rua` tag. Begin with `p=none`; move to quarantine/reject only after reviewing
aggregate reports and verifying alignment.

## Reverse DNS and connectivity

- Set the VPS provider's PTR/rDNS for the sending IPv4 address to
  `mail.testagram.site`.
- Ensure `mail.testagram.site` resolves forward to that same IPv4 address.
- Permit outbound TCP/25 from InstaBox to recipient MX hosts.
- Permit inbound TCP/25 to InstaBox and forward it to the API container's
  feedback listener on port 2525.
- Install a valid certificate for `mail.testagram.site` in the two VPS paths above;
  the deployment script mounts them read-only and enables STARTTLS automatically.
  Without those files, the receiver deliberately does not advertise STARTTLS.
- Confirm the provider does not block port 25 in either direction.

Do not proxy SMTP through an HTTP/CDN proxy. The MX target must resolve directly
to the VPS address.

## Acceptance

After records have propagated, verify:

1. `dig A mail.testagram.site`, `dig MX bounces.testagram.site`, and the three
   TXT records above.
2. `dig -x <INSTABOX_PUBLIC_IPV4>` returns `mail.testagram.site.`.
3. A controlled message to Gmail and Outlook has `spf=pass`,
   `dkim=pass`, and `dmarc=pass` in the receiving Authentication-Results.
4. A controlled hard-bounce DSN to a generated VERP address is correlated to
   exactly one outbox row and creates a hard-bounce suppression.
5. Replaying the same DSN does not create a second event or suppression.

A recipient MX accepting a message with SMTP 250 is not proof of inbox placement.
